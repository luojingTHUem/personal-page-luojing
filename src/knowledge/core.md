# AI产品经理核心知识体系整理文档

**AI产品经理核心知识体系**
本知识体系涵盖AI产品经理从岗位认知、技术原理、评测方法、工具使用、技术基础、工作方法论到电商垂类业务的全维度内容，结合企业知识库内容优化整理，适合AI产品经理能力提升参考。

**一、AI产品经理岗位认知与能力要求**
**1\.1 产品经理岗位分类与核心本质**
产品经理岗位可从三个维度划分：

- 按企业价值链：获客、留存、成交、履约、变现、经营

- 按服务对象：C端产品、B端产品、平台产品

- 按工作内容：体验型、增长型、业务型、策略型、平台型、AI产品、金融产品
产品经理的核心本质是识别价值创造过程中的问题，在业务、用户、技术之间做权衡，设计最优解决方案并推动落地。

**1\.2 AI产品经理必备技能**
**硬性技能**

- 掌握完整产品工作流程：需求调研、PRD撰写、需求评审、研发、测试、验收、上线、数仓、AB实验全链路

- 具备AI基础认知：掌握LLM、Agent、Skills、Tools、Workflow原理，能设计AI产品链路，无需深入底层算法开发

- 熟悉Agent工具使用：掌握Codex等工具的基础使用，能完成简单HTML Demo开发
**软性技能**

- 产品设计与用户洞察能力：深入理解用户需求，避免主观臆断需求

- 责任意识：对产出内容负责，谨慎使用AI工具避免输出低质量内容

AI产品经理核心职责包括搭建知识图谱、数据标准制定与质量评估、模型效果评估、Prompt与专家系统设计，区别于传统产品经理的核心是围绕数据和模型开展工作。

**1\.3 AI应用工程师（FDE）岗位说明**
FDE是AI时代催生的新岗位，核心能力要求包括：

- 业务拆解能力：能从客户模糊描述中提炼真实需求

- AI场景判断能力：识别适合AI落地的业务场景

- Demo开发与文档梳理能力：能快速完成多Agent系统的原型开发与流程梳理

- 跨角色沟通能力：实现客户需求与技术方案的双向翻译

- 项目交付与流程管理能力：推动AI项目落地

- 资产沉淀能力：梳理可复用的AI项目资产
常见误区：避免将AI视为万能入口、将Demo等同于上线、将自动生成等同于业务闭环。场景选择建议：大企业优先推进系统性AI化和Agent化改造，中小企业优先选择轻量、高ROI的AI场景落地。

**1\.4 产品经理能力提升要点**

- 避免给出无依据的“幻觉”答案，出现错误及时修正

- 避免仅依赖RAG检索信息，需具备自主思考能力

- 对业务的理解要具体可落地，避免浮于表面

- 具备Owner意识，主动明确做事目标

- 功能上线前需完整体验验收，避免仅输出长文档

- 能独立完成Demo开发是加分项，但不是核心要求

**二、AI核心技术原理：Tool / MCP / Agent / Skill**
**2\.1 Tool与MCP核心原理**
Tool是AI能力的最小执行单元，通常包含四部分：

- 名称：唯一标识能力

- 自然语言描述：帮助模型判断调用时机

- 输入Schema：规定参数名称、类型及必填性

- 执行程序：包含Python函数、HTTP接口、Shell命令、数据库查询等执行逻辑
MCP（Model Context Protocol）是Agent与工具通信的标准协议，作用是约定统一的通信方式，让Agent能够发现工具、读取Schema、发起调用并接收结果。MCP Server可同时提供多个Tool，作为标准适配器将现有能力转换为Agent可调用的工具。

**2\.2 Skill开发必备知识**
开发Skill需要掌握以下核心知识：

- Agent架构设计

- Skill与Agent评测方法，区分端到端与点到点评测

- MCP开发与数据处理逻辑

- Skill版本管理规范

- 效果衡量与AB Test方法

- 测试集构建与Rubric设计

- 意图识别逻辑

- Workflow与Agent的适用场景差异

- Agent与数据库的交互逻辑

**三、Agent / Skill 评测体系**
**3\.1 评测核心术语**

- Benchmark：固定标准试卷，用于版本验收与对比

- Eval Case：单条测试题，包含输入、前置条件、预期行为与评分规则

- Golden Task：有明确成功标准的标准任务

- Golden Set：人工确认的高质量标准评测集

- Ground Truth：判断结果对错的标准答案

- Golden Path：任务的标准执行路径，包含关键步骤、工具与调用顺序

- Seed Case：人工编写的种子题，可由AI泛化为不同表达

- Edge Case：边界场景测试题，包含空输入、极端数值等

- Adversarial Case：对抗测试题，用于验证AI的合规性

- Regression Case：历史失败修复后保留的回归测试题

- Holdout Set：不用于调优的保留测试集，防止过拟合

- Challenge Set：高难度、长链路的测试数据集
Golden Path不要求Agent调用步骤完全一致，仅需满足调用关键工具、参数正确、无多余操作、最终状态正确即可。

**3\.2 评测执行流程**

- 首次评测：先由产品、业务、研发共同定义Golden Path，选择20\~50道代表题统一评分标准，避免评判标准不一致

- 正式评测：先由机器批量评测，人工重点复核红线失败、低分、争议、版本退步的Case，随机抽查10%\~20%的机器通过Case，避免误判

- 版本迭代：Benchmark建立后，版本迭代优先自动回归，机器评测达标后再进行人工验收与小流量试用
核心逻辑：首次由人工教会机器评判标准，后续由机器先批改，人工处理难题与抽查。

**3\.3 评测数据集构建**
数据集构建流程：明确评测对象→拆解能力地图与考纲→设计覆盖矩阵→编写种子Case→AI泛化扩充→人工审核标注→冻结数据集版本→执行评测→线上失败回流。
数据集分为三类：

- Agent数据集：覆盖意图理解、Skill路由、任务规划、多轮状态、批量任务、权限、最终闭环等评测维度

- Skill数据集：覆盖触发、业务流程、工具调用、输出质量、异常兜底等评测维度

- 端到端数据集：验证Agent调用Skill、工具后业务目标是否完成
每条数据需绑定被测版本：Agent、Skill、模型、Prompt、工具、数据口径版本。

**3\.4 Skill效果评估指标**
Skill评测流程：静态检查→动态评测→优化迭代→发布上线→线上监测→坏案例回流。
评测维度分为两类：

- 方法维度：静态评测（直接检查Skill文件）、动态评测（运行测试数据后由评估器评分）

- 阶段维度：上线前离线评测（隔离环境测试）、上线后在线评测（生产环境真实流量测试）
核心评估指标包括：触发正确率、流程正确率、安全通过率、任务完成率、平均耗时。

**3\.5 本地评测环境搭建**
无专业评测平台时可搭建本地评测环境：

- 评测工作台选择：可使用VSCode\+Excel/CSV\+Codex/Claude Code的组合，实现文件管理、测试运行、报告生成

- 本地文件夹结构：包含README（评测说明与版本记录）、skills（被测Skill）、datasets（测试数据集）、rubrics（评分标准）、mock\_tools（模拟工具）、scripts（批量运行脚本）、reports（评测结果）

- 注意事项：涉及公司业务需使用脱敏数据，禁止上传真实业务数据到外部平台

**3\.6 Skill版本管理规范**
采用语义化版本管理：Major（核心逻辑不兼容变更）、Minor（新增能力，向后兼容）、Patch（Bug修复、Prompt优化）。
每个版本需记录：Skill定义文件及哈希、输入输出Schema、依赖工具与工作流版本、模型参数、知识库版本、评测报告、负责人与审核记录、灰度范围、上线/下线/回滚记录。

**四、AI工具使用与学习方法**
**4\.1 AI产品经理学习路径**

- 不建议初期直接学习长视频课程，可通过短视频快速建立AI领域认知，了解公司分布、模型原理、Agent开发、行业应用等内容

- 不建议直接使用vibecoding工具，先与AI多轮对话形成完整的功能模块与用户动线，再生成PRD指导开发

- 学习工具链：VSCode、GitHub桌面端、Homebrew、Node\.js、Git、Python

- 建议具备代码阅读能力，理解前后端文件架构

**4\.2 多AI工具协同使用**
可在VSCode中同时配置Trae、Codex、Claude Code、GitHub Copilot等工具，根据不同场景选择合适的工具，提升开发效率。

**4\.3 AI辅助文档撰写规范**
使用AI辅助撰写PRD、需求文档等内容时，需先人工撰写核心内容，再用AI进行润色，避免直接使用AI生成的内容。AI属于概率模型，无逻辑思维，直接生成的内容容易出现逻辑问题，修改润色的时间通常长于直接撰写的时间。

**4\.4 AI场景选题方法**
避免三类不适宜的AI场景：硬件/物理世界相关场景、行业门槛极高的场景、目标模糊抽象的场景。
推荐选择目标明确、可实现原型的场景：招投标信息聚合工具、专业Copilot、客户服务闭环、经营分析/内部提效、内容营销等方向。

**五、AI产品经理技术基础**
**5\.1 计算机知识学习地图**
需掌握12章计算机基础知识，覆盖前后端、数据库、接口等内容，同时需掌握AI基础、PRD撰写、Demo开发、取数、业务垂类认知等能力。

**5\.2 API接口与前后端基础**

- API是前后端交换能力的约定，GET用于查询数据，POST用于提交操作

- 幂等性：保证同一业务请求重复执行仅产生一次有效结果，可通过唯一request\_id、业务唯一键、事件唯一ID实现

- 后端请求重试常见原因：前端超时重试、用户刷新页面、网关重试、服务调用超时、消息队列重投等

**5\.3 数据库基础**

- 事务：一组必须同时成功或失败的数据库操作，保证数据一致性

- 数据一致性：不同表、服务、页面对同一业务事实的表达一致，需明确最终事实来源

- 历史数据回填：新增字段后需明确回填规则、空值处理、口径切换时间

**5\.4 数仓需求提报规范**
提数仓需求前需准备：业务背景、统计时间范围、分析对象、字段清单、指标定义、数据粒度、去重规则、状态范围、更新频率、历史回刷范围、数据使用方式、脱敏要求。
新建Hive表还需补充：源库、源表、源表负责人、主键、增量字段、字段含义、业务状态说明、是否存在删除更新。

**5\.5 SQL与埋点指标**

- 需掌握基础SQL语法，能看懂SQL查询，判断取数结果是否符合业务口径

- 核心指标定义：PV（总访问次数）、UV（去重用户数）、成功率（成功数量/发起数量）、转化率（流程上一步到下一步的转化比例）

**5\.6 研发流程**

- 研发自测：开发完成后需完成主流程、异常、接口参数、权限、重复操作、数据写入等测试

- 联调：前后端及其他系统按真实链路运行，验证接口、逻辑、交互是否匹配

- 测试：验证功能、业务规则、接口、数据、权限、兼容性、异常处理是否符合要求

- UAT验收：由产品、业务负责人、真实用户参与，验证功能是否满足业务需求

**5\.7 网关与第三方服务**

- 网关是客户端进入后端系统的统一入口，负责权限验证、请求转发、限流、日志记录、接口版本管理等

- 第三方服务是系统依赖但不由本团队维护的能力，需明确对接负责人、权限申请、失败处理、兜底策略、重试规则、数据标准、费用与调用限制

**六、产品经理工作方法论**
**6\.1 产品全流程工作规范**

- 需求阶段：接收需求→可行性评估→调研输出报告，C端产品可直接通过用户反馈挖掘需求

- 方案设计：项目启动→业务方案→内部评审→业务评审→产品方案\+Demo→产品评审→输出原型\&PRD

- 评审开发：PRD评审→UE设计/视觉评审→技术评审→用例评审→项目管理→答疑优化→开发/测试完成

- 验收发布：产品验收→用户手册→培训→UAT→灰度发布→上线

- 上线复盘：上线跟踪→项目复盘

**6\.2 数据归因下钻方法**
异常指标分析流程：定锚→拆维度→找样例→提假设→量化验证→分层根因→给出治理路径，每一步需验证指标异常的严重
